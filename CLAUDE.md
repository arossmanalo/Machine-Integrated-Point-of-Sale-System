# Laundry Shop POS

POS app for our family laundry shop. It currently runs as a Kotlin Android app on a tablet at the counter and is being rewritten in React Native.

## Working rules

- Commit after each milestone so progress isn't lost mid-task, and push to `origin` (https://github.com/arossmanalo/Machine-Integrated-Point-of-Sale-System) every time you commit.
- Do not add Claude as an author or co-author in commits (no `Co-Authored-By` lines, no "Generated with Claude" footers).
- The old Kotlin code is messy. Treat it as a reference for what the app does (features, business rules, data), not for how it should be built. It lives in a separate repo: https://github.com/arossmanalo/Laundry-Pos (reference only; don't copy it into this project or push to it).

## The React Native app

- Expo SDK 58 (React Native 0.88), TypeScript strict, Expo Router with routes in `src/app/`. Android only.
- `src/domain/`: pure business rules (pricing, 10+1 promo, payments, roles, statuses, unlock allowance, reports, Manila day boundaries). No React, no database.
- `src/db/`: Drizzle schema for expo-sqlite; migrations in `drizzle/` (`npm run db:generate` after a schema change, never edit an applied migration). Money is integer centavos; amount paid and balance are summed from `payments`, not stored.
- `src/services/`: the only code that reads or writes the database. Tests run them against in-memory SQLite (better-sqlite3).
- `src/ui/theme.ts` holds every colour, size and gap. The look is calm slate with one blue accent; IBM Plex Sans.
- Checks: `npm run typecheck`, `npm run lint`, `npm test` (or `npm run check` for all three).
- Shop decisions (2026-11-12): only Wash-Dry-Fold is sold; each load allows one washer and one dryer start; payment is not needed to start a machine; revenue counts on the day paid; admin or owner can void; only the owner PIN can override. Machines are started by assigned order (2026-11-19), not unlocked. The machine list (count and channels) is still to be decided with the hardware.
- `docs/shop-guide.md` is the guide for staff and the owner; `docs/developer-guide.md` is for the developer only.
- Developer account (2026-11-24, made secret the same day): role `DEVELOPER` has every owner right (`hasOwnerRights` in `src/domain/permissions.ts`) and is the only role with `can.manageMachines` (add/change machines, cycles, controller, Testing mode, test orders). It is built into the app, never created on a tablet: `npm run developer-login` (`scripts/developer-login.mjs`) writes `EXPO_PUBLIC_DEVELOPER_USERNAME` and `EXPO_PUBLIC_DEVELOPER_PASSWORD_HASH` (hashSecret format with `:` for `$`, 20,000 rounds) to the git-ignored `.env`, and `src/services/developerAccount.ts` reads them at bundle time. `eas update --environment production` ignores `.env`, so load it into the shell first (bash: `set -a; . ./.env; set +a` before the `eas update` line), then check the export in `dist/` contains the hash's salt; without it the update ships with no developer sign-in (happened once on 2026-11-24, republished). Nobody can give out the role. The owner sees `MachineOverview` (`src/ui/machines/MachineOverview.tsx`): pulses called "coins", no channels, timings, address or key; the owner may switch receipt scans and Multi-cycle (Simulate machines, `setSimulateMachines`, is developer only and hidden from the owner), and change only a machine's In use switch and coins (pulse count), which cycles are offered and their coins, and a dryer's top-up coins, prices and offered lengths (`saveOwnerMachineChanges`, 2026-11-24; an unticked length is saved as price 0). Pulse length and gap, run times, channels and the cycles themselves stay developer only. Customer-facing text says "support", never "developer". `docs/developer-guide.md` holds the developer and wiring docs; keep them out of `docs/shop-guide.md`. Hiding only goes as far as the app: the repo is public, and backups still hold the coin counts and key.

Restoring it replaces everything, including accounts (sample owner `owner` / `sample123`, PIN `1234`), so take a real backup first and restore it afterwards.

### Building the Android app on this PC

- `android/` is generated by `npx expo prebuild` and is not committed. Native config lives in `app.json` (plain HTTP allowed for the lock controller) and `plugins/` (release signing). After changing either, run prebuild again in the build copy and re-add the `buildStagingDirectory` line.
- The project path is too long for Windows when compiling the C++ parts (`ninja: error: mkdir ... No such file or directory`). Build from a copy in a short folder, e.g. `robocopy` the project to `D:\lpos` (exclude only the top-level `android`, `.git`, `.expo`), run prebuild there, and in its `android/app/build.gradle` add `externalNativeBuild { cmake { buildStagingDirectory "D:/c" } }` inside `android {}`. Enabling Windows long paths would be the permanent fix.
- Prebuild resets `android/gradle.properties`; set `org.gradle.jvmargs=-Xmx4096m -XX:MaxMetaspaceSize=1536m -Dfile.encoding=UTF-8` there again, or the build stalls with `OutOfMemoryError: Metaspace`.
- If the build fails with `Unable to delete file ...expo-modules-core...classes.jar`, a leftover Gradle or Kotlin daemon holds it: stop those `java` processes, delete `node_modules/expo-modules-core/android/build` in the build copy, and build with `-Pkotlin.compiler.execution.strategy=in-process` (worked 2026-11-21).
- Gradle also needs a short temp folder: `TMP=D:\gtmp TEMP=D:\gtmp GRADLE_OPTS="-Djdk.net.unixdomain.tmpdir=D:\gtmp -Djava.io.tmpdir=D:\gtmp"`, otherwise it fails with "Unable to establish loopback connection".
- A debug APK loads its JavaScript from Metro (`npx expo start` in this project, then `adb reverse tcp:8081 tcp:8081`).
- Release signing: put the keystore and `keystore.properties` (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`) in `android/`; both are git-ignored. Without them, release builds use the debug key and must not go to the shop tablet.

### Updating the tablet (EAS Update)

- The app gets over-the-air updates from EAS project `@arossmanalo/laundry-pos` on channel `production` (set in `app.json` under `updates`, with `expo-channel-name` in `requestHeaders` because the APK is built locally, not by EAS Build).
- JavaScript-only changes (screens, rules, text, almost everything in `src/`): run checks, commit, then from the project folder `npx eas-cli@latest update --channel production --environment production --platform android --message "<what changed>"`. It bundles the working tree, so publish only committed, checked code. First verified 2026-11-19: the tablet found, downloaded and restarted into an update within seconds. The tablet downloads it when the app opens and runs it from the next start; Manage › About this app › Check for updates applies it at once (employees have the same tab, labelled Settings). That section also shows which update is running.
- Native changes need a new APK: a new native package, `app.json` plugins or permissions, `modules/`, or an Expo SDK upgrade. Bump `version` in `app.json` first: `runtimeVersion` follows it (`appVersion` policy), so old APKs never get JavaScript they cannot run. Then build and install as above.
- The ESP32 sketch is separate and still goes over USB.

## Machine integration (built; LED prototype tested on the real ESP32)

### Goal

Stop employees from using the washers and dryers for personal laundry. Machines may only be used for paid customer orders.

### How it works

- The machines take a coin-style start signal: a number of pulses on their coin input. The ESP32 sends those pulses only when the POS asks for a start for an order. There are no door locks (lock/unlock was dropped on 2026-11-19 at the user's request).
- Flow (2026-11-21): employee creates the order → on the order page, **Assign machine** opens a window with the registered dryers on top and washers below (as stacked in the shop) → tapping a free machine opens the camera to scan the order's receipt QR code → it asks once ("Run Washer 1 for T0012?") → **Run machine** sends the signed start over Wi-Fi → the ESP32 sends the machine's pulses. The Machines tab does the same from a machine: tap it, scan the receipt (which picks the order), confirm. `startOrderOnMachine` checks the scanned code, assigns and starts in one go.
- Receipt QR codes (2026-11-21): `src/domain/receiptCode.ts`. Each order has a random `qrToken`; the code is `LPOS1:<order id>:<token>`, printed by `buildReceipt` as a raster picture (`qrRasterBytes`, GS v 0 in 64-row bands, drawn with `qrcode-generator`), because many cheap 58 mm printers ignore the native ESC/POS QR command. The code holds no counter: its uses are the order's allowance (one washer and one dryer per load). The service rejects a wrong or another order's code before anything is assigned or logged. **TEMPORARY:** `TEST_RECEIPT_CODE` (`LPOS1:TEST`, image in `docs/test-receipt-qr.png`) is accepted for every open order until the printer arrives, at the user's request; anyone with it can start any order, so remove it before real use. Scanning uses `expo-camera` (native, app 1.2.0). The owner or developer can switch scanning off with the `requireReceiptScan` setting (Manage › Machines, default on, saved through `setReceiptScanRequired`); `startOrderOnMachine` then takes `null` as the code.
- Dry only (2026-11-23): service `DRY_ONLY` (`DRY_ONLY_SERVICE`), priced by the `dryOnlyPricePerLoad` setting (default ₱100); `machineAllowance(order, type)` gives it dryers only. No 10+1 promo, no loyalty loads, no auto-consumed supplies. Wash-dry-fold dryers wait for the load's washer: `decideAssignment` refuses dryer n until n washes are over (`washer-first`): counted washer starts minus washers still counting down for the order (`washProgress`).
- Each load allows one washer start and one dryer start. If a start sends nothing (`rejected`, `busy`, `failed`, `not-connected`), the order stays assigned to the machine ("Did not start") so **Run machine** retries it; **Remove** takes it off. Such assignments are released when the order is voided or completed, or the machine is switched off.
- In use: each machine has a run time (`runMinutes`). A start sets `runOrderId` and `runEndsAt`; while `runEndsAt` is in the future the machine shows a countdown and cannot be assigned or started (owner override still can). **Mark as done** ends it early. Test starts set no timer.
- Dryer top-ups (2026-11-22): 5, 10, 15 or 20 minutes (`TOP_UP_CHOICES`), only while the dryer is still running for an open order (not after the timer ends or Mark as done). Each dryer has a price per length (`topUpPrice` is 5 minutes, then `topUpPrice10/15/20`; 0 means not offered) and its own pulse count per length (`topUpPulseCount` for 5 minutes, then `topUpPulses10/15/20`; migration 0009 started them at 2, 3 and 4 times the 5-minute count). A top-up adds an order item and the price to the order total and logs a `TOP_UP` row with `charge`; all of it is undone if nothing was sent. `applyTopUpPricesToDryers` copies the prices to all or selected dryers (developer only). Top-ups can also be paid with the order (2026-11-22): `orders.prepaidTopUpMinutes`/`prepaidTopUpLoads` at the shop prices in the `orderTopUpPrices` setting (saved by `saveShopTopUpPrices`, owner only, which copies them to every dryer), charged as an order item; `startMachine` adds the minutes and the dryer's top-up pulses to the start for the order's first `prepaidTopUpLoads` counted dryer starts. Without a prepaid top-up, the start screen can add one (`extraTopUp`): charged like a top-up while drying (`chargeTopUp`, its own `TOP_UP` log row) and undone with the start if nothing was sent.
- Multi-cycle (2026-11-22, own cycles 2026-11-24): the `multiCycle` setting (`setMultiCycle`, owner or developer). Washers' cycles live in `machine_cycles` (name, pulses, minutes, enabled), edited in `src/services/cycles.ts` (`addCycle` to one/all/selected washers, `updateCycles`); a new washer gets Delicates/Light/Medium/Heavy (`addDefaultCycles`). Migration 0010 copied the old fixed-cycle columns into it and left those columns unread (an older bundle can still run). `machineUsesCycles` is the one rule for asking: Multi-cycle on, a washer, at least one cycle switched on. The cycle id is picked on the confirm screen, passed to `startOrderOnMachine`, kept as `assignedCycleId` for a retry, and its name logged in `machine_unlocks.cycle`. Overrides and tests take a cycle id (else the first one switched on); `testTopUp` sends a dryer's pulses for one top-up length (Testing mode asks which).
- Daily report (Manage › Reports): `src/domain/dailyReport.ts` builds it from orders, payments, expenses and the machine log. Load n of an order is its nth counted washer (or dryer) start; nothing about loads is stored. Printed via `src/printing/dailyReportText.ts`.
- The developer keeps **Test start** (no order, logged as TEST; shown only after turning on Testing mode on the Machines tab, off by default and at each login) and the owner-PIN **override** (rewash, machine did not start; logged).

### Current phase: LED prototype

- One LED per machine stands in for the machine's coin input. The hardware side (relays or optocouplers on each machine's coin input, mounting) will be done by my dad later.
- Hardware: ESP32 DevKit (ESP-32D / WROOM-32 module, type HW-394, on a screw-terminal board with USB-C and a CH340 USB chip), LEDs each through a 220Ω resistor, with a shared GND rail. The LED is off when idle and lights only during each pulse (`ACTIVE_LEVEL = HIGH` in the sketch).
- 14 channels. Each channel is one screw terminal on the board:

  | Channel | Terminal | Green strip (USB port at the top) | ESP32 pin |
  |---|---|---|---|
  | 1 | D25 | right strip | GPIO 25 |
  | 2 | D26 | right strip | GPIO 26 |
  | 3 | D27 | right strip | GPIO 27 |
  | 4 | D32 | right strip | GPIO 32 |
  | 5 | D33 | right strip | GPIO 33 |
  | 6 | D13 | right strip | GPIO 13 |
  | 7 | D18 | left strip | GPIO 18 |
  | 8 | D19 | left strip | GPIO 19 |
  | 9 | D21 | left strip | GPIO 21 |
  | 10 | D22 | left strip | GPIO 22 |
  | 11 | D23 | left strip | GPIO 23 |
  | 12 | D4 | left strip | GPIO 4 |
  | 13 | RX2 | left strip | GPIO 16 |
  | 14 | TX2 | left strip | GPIO 17 |

- Those are all the pins that stay quiet at boot: they avoid the boot-strapping pins (0, 2, 5, 12, 15), GPIO 14 (pulses at boot, which could start a machine), flash (6–11), USB serial (1, 3) and input-only pins (34–39). The list lives in `LOCK_PINS` in the sketch and `LOCK_CHANNEL_TERMINALS` in `protocol.ts`; change both together. A WROVER board cannot use channels 13–14 (PSRAM). More than 14 machines needs an I/O expander (MCP23017 or PCF8575) or a second ESP32.
- `WiFi.setSleep(false)` is required: with modem sleep on, the tablet intermittently could not reach the ESP32.
- Connection: the ESP32 and the tablet are both on the shop Wi-Fi (2.4 GHz). The developer enters the ESP32's address and the key in Manage › Machines. The ESP32 is powered separately (USB charger).
- Fixed address (2026-11-21): the router gave the ESP32 a new address after a restart and the app lost it, so `config.h` sets `STATIC_IP`. Since the Wi-Fi change on 2026-11-22 it is 192.168.123.200 (gateway 192.168.123.1; the router hands out 192.168.123.x). After changing Wi-Fi, check the new router's range the same way: boot once without `STATIC_IP` and read the `READY <address>` line on serial. If another device ever takes .200, pick another free address, upload again and change it in the app.
- Moved from a USB-wired Arduino Uno to the ESP32 on 2026-11-19.

### HTTP protocol (the contract between app and ESP32)

- `GET /status` → `{"device":"laundry-locks","channels":14,"busy":[3],"lastAccepted":"<hex>"}`. The app checks it on connect and every 20 s, since Wi-Fi gives no unplug event. `busy` lists channels still sending pulses; `lastAccepted` is the challenge of the last start carried out.
- `GET /challenge` → `{"challenge":"<32 hex>"}`, single use, expires after 10 s.
- `POST /start`, form body `channel=<n>&pulses=<count>&onMs=<ms>&offMs=<ms>&challenge=<hex>&signature=<hex>`, where signature = hex HMAC-SHA256(key, `S<n>:<count>:<onMs>:<offMs>:<challenge>`). Replies `200 {"ok":true,"channel":n}` as soon as the start is accepted (the pulses follow), or `4xx {"ok":false,"error":"bad-channel"|"bad-pulses"|"busy"|"bad-signature"|"stale-challenge"}`. Every attempt uses up the challenge.
- Pulse limits (`PULSE_LIMITS` in `protocol.ts`, `MAX_PULSES`/`MIN_PULSE_MS`/`MAX_PULSE_MS` in the sketch): 1–50 pulses, 20–5000 ms on and off. Each machine stores its own count, on-time and off-time (Manage › Machines, defaults 1 × 500 ms / 500 ms).
- The signature is why a phone on the same Wi-Fi cannot start a machine and a captured request cannot be replayed. The ESP32 has no clock, so there are no timestamps.
- Requests time out after 3 s. A start is never sent twice. If its reply is lost, the app reads `/status`: `lastAccepted` equal to its challenge means it ran (`acked`), anything else means it did not (`failed`, nothing happened). Only when `/status` is unreachable too is the result `timeout`, which counts against the order's allowance (fail closed: no free second cycle; the owner override covers a machine that really did not start).
- `startMachine` takes the assignment off the machine in the same transaction that logs the start, so two taps send one start; it puts the assignment back only for results where nothing was sent (`rejected`, `busy`, `failed`, `not-connected`).

### React Native notes

- The machine controller is plain HTTP from JS (`fetch`), so it needs no native module. Android blocks plain HTTP in release builds unless `usesCleartextTraffic` is on (set in `app.json`).
- The receipt printer still needs a development build; Expo Go cannot load the app's own native modules.

### Architecture requirements for the integration

- Hide machine control behind an interface (`MachineController` with `connect()`, `start(channel, pulses)`, `state()`), with interchangeable implementations: `MockMachineController` for development without hardware and `WifiMachineController` for the ESP32.
- The UI and business logic must never talk to the machine controller directly.
- Starts must be tied to an order: no assigned order, no start.
- Log every start with the timestamp, machine, order, and employee.
- Owner-PIN override for legitimate non-order starts, such as rewashes or a machine that did not start. Overrides get logged too.
- Machines are configurable data (name, type washer/dryer, channel, pulses), not hard-coded.
